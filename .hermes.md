# Termini — agent working agreement

Repo root is **/home/ubuntu** (origin `https://github.com/yanksyoon/termini.git`, branch `main`).
`~/termini/` is just a folder *inside* the repo — NOT the repo root. Task paths are relative to `/home/ubuntu`.

## Delivery flow — every work task lands through a PR

Work happens on a branch; main is never committed to directly (except repo-infra bootstrap).

1. **Sync + branch:** `git fetch origin && git checkout -b wt/<task-id>-<slug> origin/main`
2. **Implement** at the exact paths named in the task.
3. **Verify first, iterate until green:** run the acceptance command(s) the task names (test suite, `python -c "import json; json.load(open('f'))"`, schema check, `curl` probe…). If it fails, fix and re-run. Nothing is done unverified.
4. **Commit — stage explicit paths only, never `git add -A`.** Workers share this checkout; `-A` sweeps up other workers' half-written files.
   `git add <path> <path> … && git commit -m "<task-id> <type>: <summary>"`
   Types: `feat` `fix` `docs` `infra` `test` `chore` `refactor`. Example: `t_260694d8 docs: controller API + telemetry contracts`.
5. **Push:** `git push -u origin HEAD`
6. **Open a PR:** `gh pr create --title "<task-id> <summary>" --body "<what / why / how verified / evidence>"`
7. **Land it — use the gate script; it refuses to merge red:** `scripts/land.sh` (or `scripts/land.sh <pr>`). It watches the PR's CI, aborts on any failing check, and squash-merges + deletes the branch only when green. Never blind-`gh pr merge`. (Server-side branch protection is unavailable on this private free-plan repo, so this script is the enforcement point.)
8. **Record on the card:** `kanban_complete` / `kanban_request_review` with
   `metadata={"commit": "<sha>", "pr": "<url>", "merge_sha": "<sha>", "files": [...], "verified_with": ["<cmd> -> <result>"]}`.

## Rules

- **Never commit secrets or runtime state:** `.hermes/`, `.ssh/`, `.env*`, `*.pem`, `*.key`, caches. A `pre-commit` hook blocks them — do **not** use `--no-verify`.
- If `index.lock` exists, another worker is committing in the shared checkout: wait a moment and retry.
- Keep each PR scoped to one card.
- If a check genuinely cannot run on this host, say so explicitly in the completion and state exactly what you did run.

## The live fleet — one window at a time

The standing fleet (controller + node-a + node-c) is **shared** by every `infra`
worker. Whoever else is on it can invalidate your run: a peer's clear-all ends your
open injection (historically filed as `cleared_by=human`, i.e. "the operator"), and a
redeploy restarts the controller, whose boot sweep expires every injection another
process was driving. Take the window *before* you touch the fleet, not after:

1. `infra/gcp/tools/live-window.sh install` — once per VM (idempotent; installs
   `/usr/local/bin/termini-live-window` and `/var/lib/termini/live-window/`).
2. `infra/gcp/tools/live-window.sh take --owner <your-task-id> --ttl 45m --purpose "<card>: <what the run proves>"`
3. Do the acceptance. Deploy with `deploy-termini-tree.sh --actor <your-task-id>`: it
   **refuses (exit 3/4, nothing written to `/opt/termini`)** when the window is held by
   another owner or not held at all. Send `X-Termini-Actor: <your-task-id>` on every
   fault inject/clear so the audit line names you (header-less callers are recorded as
   `unattributed_project_token`; the operator console sends `human`).
4. `infra/gcp/tools/live-window.sh release --owner <your-task-id>` on **every** outcome,
   including a failed run, and record the window (owner, take/release times) on the card.

A refusal is the design, not an accident: `status` names the holder, their purpose and
the expiry, and the loser exits non-zero with that text. If you need the fleet out of
turn, ask the holder on the board — nobody deletes a lease by hand, and there is no
`--force`. `live-window.sh` lives on the controller VM so the lease survives controller
restarts and stays readable while the controller is down (e.g. during a migration pause,
which is exactly when a peer is most likely to deploy on top of you).

## Reviewers / verifiers

Do not trust implementer summaries. Check out the PR branch, `git show <sha>`, confirm the files are the real deliverables, and **re-run the acceptance command against the committed state**. Approve only if it passes *on the commit*, not on uncommitted edits. Verdicts: `kanban_request_changes` with the exact failing command/output, otherwise approve and land the PR.
