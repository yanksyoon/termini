# The one post-fix raw-404 audit row: the guarded tree, via the unverified-probe path

**Card:** t_2f4b5ffe — *Explain the one post-fix raw HTTP 404 audit row
(2026-10-17T16:32:14Z) — identify the revision/process that served it.*
**Investigated:** 2026-10-17T~19:00Z, read-only, on the live controller
(`termini-controller`, 34.93.190.64) — `journalctl`, `/opt/termini` backups, the
`/data/controller.db` rows. Nothing was restarted, deployed or written on the VM.

## Answer

The row was **not** served by an older, pre-fix tree. It was served by the tree
that already carried the fail-closed guard — `DEPLOYED_COMMIT`
`8d7ac5afdd4e08d113cb6d088ef2ab599c04341f`, `controller/app/operator/executor.py`
sha256 `06e89cb3…` — by PID **201440**, started **2026-10-17T13:14:36Z** and
replaced at 17:02:12Z. Its bytecode contains `target_missing`/`refused PUT`.

It is explained by the guard's deliberately tri-state probe: at 16:32Z node-a's
LXD could not answer `GET /1.0/instances/<name>` (`None`, "could not ask"), so
`restart_instance` issued the PUT by design, and LXD answered 404. The audit then
carried LXD's raw body. The same minute's journal says the node's instance
inventory was unreadable and the operator poll was 27.56 s behind — a transient
node read failure, not an un-deployed fix.

**Decision taken (and landed):** keep shipping the write when the probe cannot
answer — "could not ask" must not become a refused remediation — but the audit
must record the target as **`target_unverified`**, never replay the raw LXD body.
That is `TARGET_UNVERIFIED` in the executor, with regression tests at the
executor and audit boundaries.

## 4. Why the guard did not fire — `instance_exists` answered "unknown"

The guard refuses only when the probe answers 404 (`exists is False`). The audit
shape proves it did not:

* a refusal is recorded with `lxd_method=GET` and `reason=target_missing`
  (`_refuse_missing_target` issues no state change); this row is `PUT` with no
  reason;
* the guard logs a `target_missing:` warning; `journalctl` between 16:30 and
  16:36 contains **none** (the next ones are at 19:01/19:14Z, on a different
  node and the current process).

What the journal does contain, 3.5 s after the rule fired, is the node's live
inventory failing to read:

```
16:32:14.531  node 01M4NZK474BVARFBXYQBMVA8GV rule oom-guard-01 FIRED:
              detection_latency=3.513s (breach=16:32:11.000Z)
16:32:14.508  operator poll falling behind: took 27.56s > interval 2.00s (nodes=4)
16:32:18.066  node 01M4NZK474BVARFBXYQBMVA8GV instance inventory unreadable
              (https://10.10.0.11:8443); keeping configured names
16:32:20.948  node … rule oom-guard-01: model decision fell back (reason=parse_error)
16:32:33.862  node … rule oom-guard-01 -> instance.restart NNB…: error
              (remediation_latency=15.767s)
```

With the inventory unreadable, the resolution kept the configured name (`_vm_id`
= the name, `NNB…`), and the executor's own probe hit the same slow/unavailable
LXD. `instance_exists` returned `None` ("could not ask"), which
`restart_instance` is documented to treat as "proceed" — turning a transient
unreadable node into a refused remediation would be a new failure mode. The PUT
was issued and LXD answered 404 with the body above.

A minute later the node was readable again and the very next decision on the same
node resolved its target normally — proof that this was a transient read failure,
not a configuration problem:

16:35:13.093  audit 01M55BFBNSRB1ZK1Z4J7EN802N result=ok

## 5. Decision and fix (landed)

Two things kept, one changed:

1. **Keep the write.** An unanswerable probe is not evidence of absence;
   refusing there would convert a slow node into a failed remediation. This is
   already pinned by `ProbeNotRefusedTest.test_5xx_probe_lets_the_write_through`.
2. **Keep the refusal.** A probe that answers 404 still refuses with no write
   (`target_missing`) — unchanged.
3. **Change what the audit says** when the write is then answered 404:
   `TARGET_UNVERIFIED` (`target_unverified`) instead of LXD's raw body. The row
   still records the write truthfully (`lxd_method=PUT`, path, body, status) and
   now carries `reason=target_unverified` plus a target-shaped detail:

   ```
   target_unverified: probe GET /1.0/instances/NNB… could not answer
   (HTTP 500: …), so PUT /1.0/instances/NNB…/state was attempted on
   https://10.10.0.11:8443 — LXD then answered 404: the target is not on this
   node. The write was attempted because a probe that cannot answer is not proof
   of absence; the audit reports the target as unverified rather than replaying
   LXD's error body.
   ```

   The detail contains no `HTTP 404` and no LXD `error` body, so the DB predicate
   `detail like '%HTTP 404%'` keeps meaning "a raw LXD 404 leaked" and stays
   empty.

Regression tests (`tests/test_operator_target_missing.py`):

* `UnverifiedProbeTest` — restart/stop/start, probe 500 + PUT 404: result
  `error`, `reason == "target_unverified"`, no `HTTP 404` / `Failed to fetch
  instance` in the detail, and the PUT **was** issued.
* `LoopRefusalTest.test_404_after_an_unanswered_probe_is_recorded_as_target_unverified`
  — the same at the audit boundary: audit `reason=target_unverified`, detail
  starts with it, operator log line (what the dashboard renders) carries it and
  no raw body.
* `tests/stub_lxd.py` gained the two knobs that model the live moment:
  `probe_unavailable` (the existence probe answers 500) and `strict_state_404`
  (a state change on an unknown name answers LXD's real 404).

Verified: `python3 -m unittest discover -s tests` → **1079 tests, OK** (the new
tests fail on the pre-fix commit with `'' != 'target_unverified'`).
