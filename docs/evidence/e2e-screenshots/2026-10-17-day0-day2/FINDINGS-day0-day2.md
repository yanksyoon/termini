## How the last blocker was cleared

The 403 had three independent causes, each found by running the thing:

1. **`NoNewPrivileges=true` in the node unit kills the snap `lxc` CLI**
   (`cannot change profile for the next exec call: Operation not permitted`), so
   the node could not mint anything the old way. → talk to LXD over its **unix
   socket** (#265).
2. **Endpoint shapes differ**: a fresh node reports `host:port`, a hand-wired one
   `https://…`. The scheme-less form made the controller's probe fail before any
   trust attempt. → normalise through `op_target.endpoint_base_url` (#265).
3. **The trust direction was wrong.** A certificate-add TOKEN minted on the node's
   admin socket is not redeemable by a second party (LXD: `403 Bad trust
   password`); a `core.trust_password` works but needs a managed secret and a
   controller→node hop inside the window where LXD has the socket up but has not
   yet bound `:8443` (measured: `Connection refused` from the controller process
   while the node's own listener probe passed). → **the node adds the controller's
   PUBLISHED certificate to its own trust store** over its admin socket
   (`GET /v1/nodes/{id}/lxd-trust-cert`, then `POST /1.0/certificates` with
   **base64 DER** — raw PEM is rejected `illegal base64`, base64 PEM `x509:
   malformed`), and the controller confirms with its own authenticated probe
   (#270).

## Numbers worth knowing before quoting this on stage

- **`register_ms` is 23.8 s on this image, not 150–245 ms.** The daemon's
  pre-registration `ensure_lxd_api()` waits for LXD: on this image the unix socket
  answers ~20–25 s before the `:8443` listener accepts, and that wait sits inside
  `register_ms`. On `termini-node-os-5` the same code path measured 245 ms. The
  `<5 s` claim is therefore **image-dependent and currently false for `os-6`…`os-8`**.
  The honest sentence is: *"registered 42 s after power-on, 24 s of which is this
  image's LXD start-up."*
- **The workload launch is ~1 min**, dominated by unpacking the 764 MiB image on a
  20 GB `pd-standard` boot disk. It is not a registry pull.
- Older measurements are not edited: `os-5` = 245 ms / 19.06 s (2026-10-17),
  archived `os-1` = 150 ms / 22.84 s (2026-10-12).

## Open, and NOT claimed

- **node-a's LXD API is unbound** (`ss` shows no `:8443` listener,
  `core.https_address` empty, unit `active`), so the operator's actions against
  node-a now audit `result=error … Connection refused`. That is the standing
  fleet's own defect, unrelated to this story; it needs
  `lxc config set core.https_address :8443` plus an LXD restart (or the current
  node daemon, which repairs it) before node-a is demoable again.
- No dashboard screenshots are in this pack — the frames were not captured in this
  run, and a frame is not evidence of the numbers above.
- The token and password trust paths remain in the code for deployments that can
  use them; this image uses the certificate path.
